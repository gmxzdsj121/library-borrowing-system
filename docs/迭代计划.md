## 1 为什么选择迭代开发

本项目的开发周期为 6 周（第1周至第6周），三名成员只能利用课余时间投入，需求（尤其是罚款宽限期、预约保留期、续借上限等业务规则）需要在实现过程中逐步对齐。若采用一次性的瀑布式开发，把需求在开工前完全冻结，一旦规则调整就要返工数据库与业务代码，风险集中在交付末期。因此小组采用迭代模型：

- 每轮迭代约两周，固定节奏，每轮结束交付一个可运行的版本并组织评审；
- `master` 主干始终保持可运行、可演示，功能开发一律在 `feature/*` 分支完成；
- 每轮迭代结束同步修订报告对应章节，做到"代码写了什么，报告就写什么"；
- 业务规则在迭代二中先用单元测试固定口径，再由界面调用，避免反复口头确认。

## 4 迭代完成定义（DoD）

一项任务只有同时满足以下五条，才在迭代评审中标记为"完成"：

1. 代码已提交到对应的 `feature/*` 分支，提交信息统一使用 `feat` / `fix` / `docs` / `test` 前缀；
2. 新增代码有对应的单元测试或接口测试，`python test/run_tests.py` 全部通过；
3. `master` 分支上可以直接运行 `python start.py` 启动，不依赖未提交的本地文件；
4. 涉及业务规则的，规则数值写在 `src/config.py` 中，不散落在代码里；
5. 报告或 `docs/` 下的文档已同步更新，不存在"代码已改、文档没改"的情况。

## 5 迭代二、三的范围预告

本文件只登记范围，不展开设计。迭代二聚焦借阅业务五条链路（借阅登记、归还处理、逾期罚款、续借、预约借书）与系统设计章节；迭代三聚焦统计报表、通知公告、性能与安全测试、部署与演示。具体任务在对应迭代的计划会上拆分并补充到第 3 节。

## 6 风险与应对

| 风险 | 影响 | 应对措施 |
| --- | --- | --- |
| 三人课余时间不重合，联调窗口少 | 集成阶段集中出问题 | 主干保持可运行；每个分支合并前先本地跑完整测试；接口契约在第 3 节任务中先写清楚 |
| 借阅规则（宽限期、单价、保留期）反复调整 | 返工业务代码 | 规则数值集中到 `src/config.py`；迭代二用单元测试固定口径，规则变更时先改测试再改代码 |
| 课程机房无法联网安装第三方库 | 演示当天启动失败 | 全栈仅使用 Python 标准库（`http.server`、`sqlite3`、`hashlib`），`requirements.txt` 无第三方依赖 |
| SQLite 并发写入能力有限 | 50 并发指标不达标 | 读多写少场景使用独立连接 + 忙等重试；性能测试在第 5 周提前做，不达标则调整连接与索引策略 |
| 报告与代码不同步 | 答辩时对不上 | 每轮迭代结束当天更新报告对应章节，由组长统稿核对 FR 编号 |
